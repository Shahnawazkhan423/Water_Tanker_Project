## Finding 1 — Secrets in Version Control

**Severity:** 🔴 Critical  
**Location:** `.env` (committed to git)

```
SECRET_KEY=django-insecure-&-!df1u3%1hltb53gnq3yx_s2@xxt*oyg(wm+i&6p(lmkp2l8z
EMAIL_HOST_USER=shahnawazkhan96850@gmail.com
EMAIL_HOST_PASSWORD=kddz mxrq djxg ryzf
DB_PASSWORD=postgres123
```

**Risk:** Anyone with read access to the repository can:
- Forge Django session/CSRF cookies using the `SECRET_KEY`
- Send emails as the platform's Gmail account
- Access the PostgreSQL database directly

**Mitigation:**
1. Rotate `SECRET_KEY` immediately (generate a new one, deploy)
2. Revoke and regenerate the Gmail App Password
3. Remove `.env` from git history (`git filter-branch` or `git-filter-repo`)
4. Add `.env` to `.gitignore` (already present in `.gitignore` — verify it was added after the commit)
5. Provide `.env.example` with placeholder values

## Finding 2 — CSRF Protection Disabled on Most Views

**Severity:** 🟠 High  
**Location:** Both `Customer/views.py` and `Supplier/views.py`

Most views have `@csrf_exempt` applied:

```python
# Customer/views.py
@csrf_exempt
def login_view(request): ...

@csrf_exempt
def logout_view(request): ...

@csrf_exempt
def booking(request): ...

# Supplier/views.py
@csrf_exempt
def register_view(request): ...

@csrf_exempt
def login_view(request): ...

@csrf_exempt
def tanker_detail_view(request): ...
```

**Risk:** Cross-Site Request Forgery attacks. A malicious page can submit forms to these endpoints on behalf of a logged-in user. For example, a CSRF attack could trigger a booking, cancel an order, or upload documents without the user's knowledge.

**Note:** Django's `CsrfViewMiddleware` is present in the middleware stack and templates appear to include `{% csrf_token %}` in most forms. The `@csrf_exempt` decorators bypass the middleware for no apparent reason.

**Mitigation:** Remove `@csrf_exempt` from all views that are not genuinely public, stateless, JSON endpoints. The CSRF tokens in templates will handle validation automatically.

## Finding 3 — Password Reset URL Hardcoded to Localhost

**Severity:** 🟠 High  
**Location:** `Customer/helper.py:8`

```python
reset_link = f"http://127.0.0.1:8000/Customer/reset-password/{token}/"
```

**Risk:** In production, password reset emails will contain `http://127.0.0.1:8000` — links that users cannot click (they point to the server, not the internet). The password reset feature is completely broken in production.

**Mitigation:**
```python
reset_link = request.build_absolute_uri(
    reverse('reset_password', kwargs={'token': token})
)
```

## Finding 4 — Supplier Login Missing Role Guard

**Severity:** 🟠 High  
**Location:** `Supplier/views.py:144`

```python
def login_view(request):
    user = authenticate(request, email=email, password=password)
    if user is not None and isinstance(user, CustomUser):  # ← Always True!
        login(request, user)
        return redirect('Home')
```

**Risk:** A customer can log into the supplier portal using their customer credentials. Once inside the supplier portal, they would be displayed supplier views. Depending on the view guards, they might be able to see or manipulate supplier data.

**Mitigation:**
```python
if user is not None and user.user_type == 'supplier':
    login(request, user)
    return redirect('Home')
```

## Finding 5 — Password Reset Token Never Expires

**Severity:** 🟡 Medium  
**Location:** `Customer/views.py:258-295`, `Customer/models.py:22`

`CustomerProfile.forgot_password_token` has no expiry field. Tokens generated by `uuid.uuid4()` remain valid until explicitly used.

**Risk:** If a reset email is intercepted, the link remains usable indefinitely. An attacker who gains access to old emails could still reset a user's password months later.

**Mitigation:** Add `forgot_password_token_created_at = DateTimeField(null=True)`. In `reset_password` view, reject tokens older than 1 hour.

## Finding 6 — Session Cookie Not Secure

**Severity:** 🟡 Medium  
**Location:** `Water_Tanker_Project/settings.py:56`

```python
SESSION_COOKIE_SECURE = False
```

**Risk:** Session cookies will be transmitted over HTTP (not just HTTPS). In environments without HTTPS enforcement (e.g., HTTP-only load balancers, misconfigured proxies), session tokens can be intercepted via network sniffing.

**Mitigation:** Set `SESSION_COOKIE_SECURE = True` in production settings. Ensure HTTPS is enforced at the load balancer or reverse proxy.

## Finding 7 — Debug Mode in Committed Configuration

**Severity:** 🟡 Medium  
**Location:** `.env:2`

```
DEBUG=True
```

**Risk:** If this `.env` is deployed to production (which is likely given it's the only env file):
- Django shows full stack traces to users on errors
- Database schema, local filesystem paths, and installed app list are exposed
- Performance implications (no request caching, verbose SQL logging)

**Mitigation:** Set `DEBUG=False` in production. Use a separate `.env.production` file or environment-specific deployment secrets.

## Finding 8 — Missing `@login_required` on cancel_order

**Severity:** 🟢 Low  
**Location:** `Customer/views.py:211`

```python
def cancel_order(request, order_id):
    order = get_object_or_404(OrderDetail, id=order_id, user=request.user)
```

**Risk:** Unauthenticated users can hit this endpoint. `request.user` will be an `AnonymousUser` — the `get_object_or_404` filter `user=request.user` will likely return 404 (since orders have real user FKs), but this is not an explicit authentication guard.

**Mitigation:** Add `@login_required(login_url='login')` decorator.

## Finding 9 — Bug in cancel_order Receiver (Attribute Error)

**Severity:** 🟡 Medium (runtime error)  
**Location:** `Customer/receivers.py:9`

```python
message=f"Order ID {order_instance.id} has been cancelled by customer {customer_user.name}."
```

`CustomUser` has no `.name` attribute (it has `.first_name` and `.last_name`). This will raise an `AttributeError` at runtime when a customer cancels an order that has an assigned driver (supplier).

**Mitigation:**
```python
message=f"Order ID {order_instance.id} has been cancelled by customer {customer_user.first_name} {customer_user.last_name}."
```

## Finding 10 — File Upload Type Validation Is Extension-Only

**Severity:** 🟢 Low  
**Location:** `Supplier/forms.py:169-178`

```python
def _clean_file_field(self, field_name):
    name, ext = os.path.splitext(uploaded_file.name)
    if ext.lower() not in ALLOWED_FILE_EXTENSIONS:
        raise ValidationError(...)
```

**Risk:** Extension-based validation is bypassable. An attacker can rename a malicious file to `.jpg` and upload it. The content is never inspected.

**Mitigation:** Use `python-magic` (already in Dockerfile runtime as `libmagic1`) to validate MIME type based on file content:
```python
import magic
mime = magic.from_buffer(uploaded_file.read(2048), mime=True)
if mime not in ['image/jpeg', 'image/png']:
    raise ValidationError(...)
```

Note: `libmagic-dev` and `libmagic1` are installed in the Dockerfile but `python-magic` is not in `requirements.txt` — this appears to be a planned but unimplemented feature.

## Finding 11 — Debug Print Statements Expose Data

**Severity:** 🟢 Low  
**Location:** `Customer/views.py:231`, `Customer/views.py:248`

```python
print("detail:---", order_canceled_by_customer)   # Prints signal object
print("Email entered:", email)                      # Logs user email to stdout
```

**Risk:** In production, these print to Gunicorn's stdout/logs — email addresses are PII and should not appear in application logs without redaction.

**Mitigation:** Remove all `print()` statements. Use `logger.debug()` with appropriate log level configuration for dev/prod.

## Finding 12 — Session Age Inconsistency

**Severity:** 🔵 Info  
**Location:** `settings.py:168` vs `middleware/session_override.py:39`

Settings sets `SESSION_COOKIE_AGE = 3600` (1 hour), but the middleware sets cookie `max_age = 86400` (24 hours). The middleware overrides the Django setting.

**Risk:** Sessions last 24 hours instead of the intended 1 hour. If a device is lost/stolen, an attacker has 24 hours to use the active session (vs 1 hour).

---

## Finding 13 — No Rate Limiting

**Severity:** 🟡 Medium  
**Location:** Login views, forgot_password view

No rate limiting is applied to:
- Login attempts (brute force possible)
- Password reset requests (email spam possible)
- Registration endpoints (account creation spam)

**Mitigation:** Use `django-ratelimit` or implement per-IP/per-email throttling on these endpoints.
